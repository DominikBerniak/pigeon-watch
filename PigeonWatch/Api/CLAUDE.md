# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Scope: `PigeonWatch/Api/` only — the ASP.NET Core Web API. See `@PigeonWatch/CLAUDE.md` for what PigeonWatch is and how Api/Frontend fit together.

## What this owns

ASP.NET Core Web API (.NET 10). Owns auth and the status-workflow/urgency-ranking business logic for sightings (the status workflow and criticality levels are defined in `@context/foundation/prd.md`, Business Logic). Solution: `PigeonWatchApi.slnx` with six layered projects plus three test projects: `ArchitectureTests/PigeonWatch.ArchitectureTests.csproj`, `UnitTests/PigeonWatch.UnitTests.csproj` (xUnit, NSubstitute, SQLite in-memory for the user store) and `IntegrationTests/PigeonWatch.IntegrationTests.csproj` (xUnit, `WebApplicationFactory<Program>` on SQLite in-memory).

Data layer: EF Core (SQL Server) via `Data/PigeonWatchDbContext.cs`, migrations in `Data/Migrations/`. Three tables:

- `USER_ACCOUNT`, persisted for ASP.NET Core Identity through the custom `Data/Identity/PigeonWatchUserStore.cs` (no `IdentityDbContext`, no stock Identity tables).
- `SIGHTING` (migration `AddSighting`): `REPORTER_ID` FK to `USER_ACCOUNT.ID` (restrict delete; the `Reporter` navigation supplies the display name), nullable `NAME`, `DESCRIPTION`, `BEHAVIOUR`, `LATITUDE`/`LONGITUDE` as `double`, `STATUS`/`CRITICALITY` as `int`, and a nullable `PHOTO_BLOB_NAME` (max 64, migration `AddSightingPhoto`; the business object and the API expose only `HasPhoto`, never the blob name). Indexes on `(LATITUDE, LONGITUDE)` for the nearby box and `(REPORTER_ID, CREATE_DATE)` for the cooldown lookup and the user's own list. No spatial type or index (no NetTopologySuite).
- `SIGHTING_COMMENT` (migration `AddSightingComment`): `SIGHTING_ID` FK to `SIGHTING.ID` and `AUTHOR_ID` FK to `USER_ACCOUNT.ID` (both restrict delete; the `Author` navigation supplies the display name), `TEXT` (max 500), nullable `EDITED_AT` (set only by an edit) and `DELETED_AT` (set only by a soft delete). Indexes on `(SIGHTING_ID, CREATE_DATE)` for the list and `(AUTHOR_ID, CREATE_DATE)` for the comment cooldown. Rows are never hard-deleted.

Auth: Identity bearer tokens (`MapIdentityApi`, no cookies). The bearer and refresh tokens are protected by the Data Protection key ring, so there is no signing key to configure. The endpoint surface is:

- `POST account/register` (anonymous, rate limited): our own action, because the built-in `/register` cannot carry a display name.
- `POST auth/login` (rate limited) and `POST auth/refresh`: the only Identity endpoints exposed. `MapPigeonWatch` maps `MapIdentityApi` under `auth`; a `.Finally` convention replaces every other Identity route's request delegate with a 404 (before body binding) and returns 400 when `useCookies`/`useSessionCookies` is set to anything but `false`.
- `GET configuration/client` (anonymous, `Cache-Control: public, max-age=300`): validation rules from `BusinessObjects/AccountRules.cs`, the sighting rules (`sightingRules`: field lengths, cooldown seconds, nearby radius, `photoMaxBytes`, `photoMaxDimension` and `photoAllowedContentTypes` as an array) from `BusinessObjects/SightingRules.cs`, and the comment rules (`commentRules`: `textMaxLength`, `cooldownSeconds`, `pageSize`) from `BusinessObjects/SightingCommentRules.cs`, never user data.
- `GET configuration/general` (authorized, `Cache-Control: private, no-store`): the current user (id, email, display name, roles from token claims). There is no `/me` endpoint.
- `GET resources/{culture}` (anonymous, `Cache-Control: public, max-age=300`, `Content-Language`): the UI label map; see "UI labels" below.
- `POST sightings` (`multipart/form-data`, with an optional `photo` part): creates a sighting for the current user and returns 201 with `SightingModel` and a `Location` header; see "Sightings" and "Sighting photos" below for the failures.
- `GET sightings/{id:guid}`: one `SightingModel`, or 404.
- `GET sightings/{id:guid}/photo`: the stored photo as an `image/jpeg` stream, or 404 when the sighting or its photo does not exist.
- `GET sightings/{id:guid}/photo/thumbnail`: the stored square thumbnail (at most 160 px) as an `image/jpeg` stream, created and stored on first request when it is missing, or 404 when the sighting, its photo or the full photo blob does not exist; see "Sighting photos".
- `GET sightings/nearby?latitude=&longitude=[&statuses=][&criticalities=]` (latitude and longitude required and range-validated): up to 200 newest open sightings within 10 km of the point, as `SightingListModel`. `statuses` and `criticalities` are optional repeatable `int` filters (`?statuses=1&statuses=2&criticalities=3`); omitted or empty means no filter, so a request without them returns the same result as before. A resolved or undefined status, or an undefined criticality, is a 400 (`InvalidFilterStatus`, `InvalidFilterCriticality`).
- `POST sightings/list` (JSON body `{ latitude, longitude, statuses?, criticalities?, page?, pageSize? }`; latitude and longitude required and range-validated): one page of the sightings within 10 km of the point, as `SightingPageModel` (`items`, `totalCount`), ordered most urgent first (criticality descending), then oldest report first (`CREATE_DATE` ascending), then `ID`. `page` is 1-based (default 1) and `pageSize` is 10, 20 or 30 (default 10). Empty or omitted `statuses` means the five open statuses; any of the nine statuses is accepted, so resolved sightings can be listed on request. A page past the end is `200` with empty `items` and the real `totalCount`. An undefined status or criticality, a page below 1 or another page size is a 400 (`InvalidFilterStatus`, `InvalidFilterCriticality`, `InvalidPage`, `InvalidPageSize`); a missing or out-of-range coordinate is a model-binding 400.
- `GET sightings/mine`: up to 50 of the current user's newest sightings, any status, as `SightingListModel`.
- `GET sightings/{sightingId:guid}/comments?page=` (`page` 1-based, default 1): one page of 20 comments, newest first, as `SightingCommentPageModel` (`items`, `totalCount`); see "Sighting comments".
- `POST sightings/{sightingId:guid}/comments` (JSON `{ text }`): adds a comment as the current user and returns 201 with `SightingCommentModel` and a `Location` header pointing at the list.
- `PUT sightings/{sightingId:guid}/comments/{commentId:guid}` (JSON `{ text }`): edits the caller's own comment and returns 200 with the model.
- `DELETE sightings/{sightingId:guid}/comments/{commentId:guid}`: soft-deletes the caller's own comment and returns 200 with the placeholder model.
- `POST client-errors` (anonymous, rate limited by the `clientErrors` policy, body capped at 2 KB): the SPA's error report (`ClientErrorsController`). The body is a closed allowlist (`kind`, `context`, `httpStatus`, `errorName`, `traceId`, `route`, `sessionId`; see `ClientErrorReportModel`), the answer is `202` with no body, and the server only logs it: `fallback` reports at Information, every other kind at Warning, never Error, so a client report cannot page anyone.

All seven `sightings` endpoints are `[Authorize]` (`SightingsController`), and the reads (the photo and the thumbnail included) send `Cache-Control: private, no-store`. The four comment endpoints are `[Authorize]` too (`SightingCommentsController`), and the list sends `Cache-Control: private, no-store`. `SightingModel` carries the reporter's display name and `hasPhoto`, never the reporter id, the email or the photo's blob name.

The `auth` rate-limit policy (`WebApi/RateLimiting/RateLimitPolicyNames.cs`, configured in `Program.cs`) allows 10 requests per minute per client IP for login and register; `auth/refresh` is exempt. The separate `clientErrors` policy allows 20 requests per minute per client IP for `POST client-errors`, in its own bucket so error reports never use up the login budget. A database that is paused or unreachable surfaces as `503` ProblemDetails with `Retry-After: 10` through `Data/Diagnostics/DatabaseUnavailableExceptionHandler.cs`; other exceptions stay `500`.

Auditing records the user id: `Data/Auditing/HttpContextCurrentUserProvider.cs` returns the `ClaimTypes.NameIdentifier` of the current request, or `SYSTEM` for anonymous saves (registration, failed-login lockout counters).

## Sightings

- **Rules** live in the const-only `BusinessObjects/SightingRules.cs`: name 60, description 1000, behaviour 500, cooldown 60 s, nearby radius 10 km, nearby cap 200 (applied after the status and criticality filters), mine cap 50, list page sizes 10, 20 and 30 (`ListPageSizeSmall`, `ListPageSizeMedium`, `ListPageSizeLarge`) with `ListDefaultPageSize` 10. Change a limit there; the request model, the entity and the client configuration read it (the list page sizes are not in the client configuration; the SPA mirrors them).
- **Status and criticality are integers end to end.** `SightingStatus` (Spotted 1, Caught 2, AtTheVet 3, InHomeCare 4, AwaitingAdoption 5, Adopted 6, Released 7, PassedAway 8, NotFound 9) and `SightingCriticality` (Monitor 1, NeedsHelpSoon 2, Urgent 3) have explicit values, are stored as `int` columns, and cross the wire as plain `int` fields, because API models may not use `BusinessObjects` types: `CreateSightingRequestMapper` and `NearbySightingsRequestMapper` cast in and `SightingViewModelCreator` casts out. Never renumber or reuse a value; the database rows and the SPA's label maps (`Frontend/src/app/features/sightings/sighting.types.ts`) depend on them.
- **Workflow**: `BusinessLogic/Services/SightingStatusTransitionProvider.cs` holds the PRD transition graph as a `static readonly` map in a non-static, injected class, plus the resolved set (Adopted, Released, PassedAway, NotFound), the valid initial statuses (Spotted, Caught) and the criticality rank. Reuse it; do not re-encode the graph. No endpoint changes a status yet.
- **Nearby**: `SightingService.GetNearbyAsync` validates the optional filters (statuses must be open, criticalities defined), then asks the repository for sightings inside a latitude/longitude box from `GeoDistanceCalculator` with the requested statuses (or every non-resolved status when none are requested) and, when requested, a criticality predicate in the same query, so the box row cap counts matching rows only; then keeps those within the exact great-circle (haversine) radius, newest first, capped. Longitude wrap at the antimeridian and polar latitudes are not handled (accepted for a Poland-scoped MVP).
- **List**: `SightingService.GetListPageAsync` validates the query (any defined status, defined criticalities, page from 1, page size from the `static readonly` set on the service), resolves empty statuses to the open ones, builds a `GeoRadiusFilter` with `GeoDistanceCalculator.GetRadiusFilter` and asks `SightingRepository.ListPageInRadiusAsync` for the page. The repository applies the box, the exact haversine radius (in SQL: only `Sin`/`Cos` of the row columns against constants computed in C#), the status and criticality filters, counts the matches and then orders and pages in SQL. It orders by the stored `CRITICALITY` value, which is only correct while the `SightingCriticality` values equal the provider's criticality ranks; a unit test pins that. The list has no row cap. Nearby keeps its own query, ordering and cap.
- **Cooldown**: `SightingService.CreateAsync` reads the reporter's latest `CREATE_DATE` and refuses a create when less than `CooldownSeconds` have elapsed on the injected `TimeProvider` (exactly 60 s is allowed). The arithmetic lives in `SubmissionCooldownProvider` (`GetRetryAfterSeconds(latestSubmission)`), shared with the comment cooldown; each caller reads its own latest submission. It is a per-user business rule, not the rate limiter, and it is not atomic: two truly concurrent submissions may both pass (accepted).
- **Failures**: like account failures, they are 400 `ValidationProblemDetails` keyed by error code from `SightingErrorCodes` (`CooldownActive`, `InvalidInitialStatus`, `InvalidCriticality`, `InvalidLocation`, on nearby and list `InvalidFilterStatus`, `InvalidFilterCriticality`, and on list `InvalidPage`, `InvalidPageSize`). `CooldownActive` also carries the remaining whole seconds as the `retryAfterSeconds` extension on the problem body and as a `Retry-After` header, because `ModelState` holds only descriptions; the SPA reads `retryAfterSeconds` into its message placeholder, so keep that name. `ReporterNotFound` (a token for a deleted user) becomes 401. Error codes are PascalCase constants, the photo codes included.

## Sighting comments

Introduced by the `comment-on-sighting` change (S-07).

- **Rules** live in the const-only `BusinessObjects/SightingCommentRules.cs`: text 500, page size 20. The cooldown reuses `SightingRules.CooldownSeconds` (60 s).
- **Separate clocks.** The comment cooldown reads only `SIGHTING_COMMENT` (`GetLatestSubmissionDateByAuthorAsync`: the newest `CREATE_DATE` or `EDITED_AT` over all the author's comments, soft-deleted rows included, so delete-and-repost cannot bypass it); the sighting cooldown reads only `SIGHTING`. Reporting a sighting never blocks a comment and the other way round. A post and an edit count as submissions; a delete does not and is never throttled.
- **Order of checks** (`SightingCommentService`): trim and validate the text (`CommentTextRequired`, `CommentTextTooLong`), then existence (`SightingNotFound` on list and post; `CommentNotFound` on edit and delete when the comment is missing, belongs to another sighting or is already deleted), then authorship (`NotCommentAuthor`, edit and delete only), then the cooldown (`CooldownActive`, post and edit only), then the write. An edit whose trimmed text equals the stored text succeeds after the authorship check with the comment as it is: no write, no `EDITED_AT` and no cooldown check. A rejected request writes nothing. Edit sets `EDITED_AT`, delete sets `DELETED_AT`; neither relies on the audit columns.
- **Status mapping** (`SightingCommentsController`): `SightingNotFound` and `CommentNotFound` are 404 (logged at Information), `NotCommentAuthor` is 403 (logged at Warning with the route), `AuthorNotFound` is 401, and every other code is a 400 `ValidationProblemDetails` keyed by code, with `retryAfterSeconds` and `Retry-After` on `CooldownActive`. `InvalidPage` is logged at Warning; `CooldownActive`, `CommentTextRequired` and `CommentTextTooLong` are not logged. The request model allows empty text (`[Required(AllowEmptyStrings = true)]`) so that whitespace-only text reaches the service as `CommentTextRequired`; over 500 characters (untrimmed, matching the SPA's `maxLength`) is a model-binding 400 keyed `Text`, so the service's trimmed `CommentTextTooLong` check only guards non-HTTP callers.
- **Wire shape.** `SightingCommentModel` is `{ id, text, authorDisplayName, createdAt, editedAt, isDeleted, isMine }`; `SightingCommentViewModelCreator` computes `isMine` against the caller. It never carries the author id, the email or an audit column. A deleted comment stays in the list and in `totalCount` as a placeholder: `text`, `authorDisplayName` and `editedAt` are null, `isDeleted` is true and `isMine` is false. The list is ordered `CREATE_DATE` descending, then `ID` descending.
- **Tests.** `SightingCommentContractTests` cover authorship with read-back, paging, the placeholder, the separate clocks and an explicit check that no comment response carries `authorId`, `createUser`, `updateUser` or a user id (`ResponseLeakScanner` looks for emails only). The four endpoints are in `EndpointFixtureRegistry`; `FixtureContext.CommentId` is a comment Alice posts on her own sighting through `TestUser.CreateCommentAsync`. The comment cooldown must stay a 400: the privacy sweep sends repeated valid posts and fails on any 429.

## Sighting photos

Introduced by the `attach-sighting-photo` change (S-04).

- **Store seam.** `Data/Storage/Interfaces/ISightingPhotoStore.cs` (`SaveAsync`, `OpenReadAsync`, `DeleteAsync` by blob name) is the only way photo bytes are stored. `AddData` registers it as a singleton factory from the `BlobStorage` settings (`BlobStorageOptions`): `LocalFolderSightingPhotoStore` when `BlobStorage:LocalDirectory` is set (Development; `appsettings.Development.json` uses `LocalPhotos`), otherwise `AzureBlobSightingPhotoStore`, which builds a `BlobContainerClient` from `BlobStorage:ServiceUri` and `BlobStorage:ContainerName` with `DefaultAzureCredential` (managed identity, never a key) and uploads as `image/jpeg`. `BlobStorageOptionsValidator` fails start-up outside Development unless `ServiceUri` and `ContainerName` are set and `LocalDirectory` is empty; in Development it needs one of the two. `LocalFolderSightingPhotoStore` accepts only `<guid>.jpg` and `<guid>-thumb.jpg` names and throws `ArgumentException` for anything else. Integration tests swap in `InMemorySightingPhotoStore`, which can be switched to fail as a whole (`IsUnavailable`) or for chosen blob names (`FailSaveWhen`), and records the names it saved (`SavedBlobNames`). The stores are named `*PhotoStore`, which is not a role suffix, so `ServiceRegistrationTests` does not require an exact-type registration for them.
- **Storage outage.** The stores wrap transport, authentication and timeout failures (in `AzureBlobSightingPhotoStore`, a `RequestFailedException` only with status 0, 408, 429 or 5xx; another 4xx such as a missing role or container is a configuration fault and stays a 500; in `LocalFolderSightingPhotoStore`, `IOException` and `UnauthorizedAccessException`) in `PhotoStorageUnavailableException` (in `BusinessObjects`, inner exception kept). `Data/Diagnostics/PhotoStorageUnavailableExceptionHandler.cs` turns it into a 503 `ValidationProblemDetails` keyed `PhotoStorageUnavailable` with `Retry-After: 10` and an Error log entry carrying the cause; nothing is saved. The SPA's warm-up interceptor passes this 503 straight through instead of treating it as a cold start, so keep the key name.
- **Multipart create contract.** `Create([FromForm] CreateSightingRequestModel request, ...)` takes `multipart/form-data` with the existing fields and an optional `IFormFile Photo`. An absent or empty photo part means no photo, and the create behaves as before. A photo is checked from its bytes (JPEG, PNG or WebP; `PhotoAllowedContentTypes` is a comma-separated const in `SightingRules`, served to the SPA as an array), at most `PhotoMaxBytes` (2 MB) and `PhotoMaxPixels` (16 megapixels, read from the header before decoding), then `PhotoNormalizationProvider` decodes it at the smallest eighth-step scale whose longest edge is still at least 1600 px (JPEG and WebP scale during decode, so a 4000×3000 photo decodes at 2000×1500; PNG decodes at full size, which the 16 MP cap bounds at about 64 MB) and re-encodes it with SkiaSharp as a JPEG at quality 85 with the orientation applied, no metadata and the longest edge at most 1600 px. Failures are 400 `PhotoTooLarge`, `PhotoUnsupportedType` or `PhotoUnreadable`, logged at Warning. Order: field validation and the cooldown first (a rejected request never touches storage), then normalize and create the thumbnail, store the photo under a new GUID blob name, store the thumbnail as `<guid>-thumb.jpg`, insert the row. If the thumbnail save fails (a `PhotoStorageUnavailable` 503 like any storage outage), the insert fails, or the reporter is not found, both blobs are deleted; each failed delete is logged at Error with its cause and leaves an orphan.
- **No 413.** `[RequestSizeLimit]` and `[RequestFormLimits]` cap the body at `PhotoRequestMaxBytes` (`PhotoMaxBytes + 512 KB`), but MVC form binding turns the overflow into a ModelState error, so `AddWebApi` replaces `InvalidModelStateResponseFactory` for that case: an over-limit multipart body with a `Content-Length` is a 400 keyed `PhotoTooLarge`. A chunked upload without `Content-Length` still gets the generic 400. The SPA maps only `PhotoTooLarge`.
- **Invariant-culture form binding.** `WebApi/ModelBinding/InvariantCultureFormValueProviderFactory` replaces MVC's `FormValueProviderFactory`, because form values otherwise bind in the server culture (pl-PL rejected `52.2297`). `CancellationTokenTests` carries one pinned allow-list entry for `IValueProviderFactory.CreateValueProviderAsync`, the framework interface method it implements.
- **Photo read.** `SightingService.OpenPhotoAsync` returns null when the sighting has no photo or the blob is missing (a missing blob is logged at Warning), and the action answers 404.
- **Thumbnails** (`sighting-row-photo-thumbnail`). `PhotoThumbnailProvider` (SkiaSharp) decodes the normalized JPEG at the smallest eighth-step scale whose shorter edge still covers the thumbnail (a 1600×1200 photo decodes at 400×300, falling back to full size), crops the centred square, scales it to `PhotoThumbnailSize` (160 px) without upscaling a smaller photo and encodes it at `PhotoThumbnailJpegQuality` (70); undecodable input throws, because the input is always our own JPEG. Thumbnails are created at upload so that serving one costs no CPU on the F1 plan; nothing resizes per request, and the responses stay `private, no-store`. The blob name is derived from `PhotoBlobName` (`SightingRules.PhotoBlobExtension` and `PhotoThumbnailBlobSuffix`), so there is no column and no migration. `SightingService.OpenPhotoThumbnailAsync` returns null when the sighting has no photo, streams the stored thumbnail when it exists, and otherwise (a photo uploaded before thumbnails existed) reads the full photo, creates the thumbnail, stores it and returns its bytes. A storage outage while saving that thumbnail (`PhotoStorageUnavailableException`) is logged at Error with its cause and the bytes are still served (it is created again on the next request); any other fault from the save fails the request, and a missing full photo is logged at Warning and answers 404. There is no backfill job.
- **Accepted limitations** (impl-review F9). A process crash between storing the blobs and inserting the row leaves orphan blobs, and nothing sweeps them up (the compensating delete runs only for failures the request sees). `LocalFolderSightingPhotoStore` leaves a partial file when a save is cancelled (Development only); a partial `-thumb.jpg` left by a cancelled create-on-miss exists, so it is served from then on and never created again (delete it by hand), and two concurrent first requests for the same thumbnail can collide on the exclusive file lock and log a `PhotoStorageUnavailableException` (impl-review F4 of `sighting-row-photo-thumbnail`). A storage failure while a photo or thumbnail is streaming, after the headers are sent, truncates the response instead of returning a 503.
- **Dependency pin.** `System.Security.Cryptography.Pkcs` 10.0.13 is pinned in `Data` to clear a transitive advisory that came in through SqlClient.

## Architecture

Six projects under `PigeonWatch/Api/`, each with matching root namespace and assembly name `PigeonWatch.<Project>`:

| Project | May contain | Must not contain or use |
| --- | --- | --- |
| `WebApi.Host` | The deployed ASP.NET Core host and EF startup project: `Program.cs`, appsettings, launch settings, user-secrets id, pipeline, MVC, Swagger, CORS, rate limiter. Calls only `AddPigeonWatch(builder.Configuration)` for application services. | Any `PigeonWatch.Data` or `PigeonWatch.BusinessLogic` type, EF Core. |
| `WebApi` | Controllers, API models, view model creators, mappers. | `PigeonWatch.Data` types, `PigeonWatch.DependencyInjection`, EF Core, DI registration code, startup code. |
| `DependencyInjection` | The `IServiceCollection` extension classes: `AddData`, `AddBusinessLogic`, `AddWebApi`, `AddAccounts` (Identity options and user store), composed by the single public entry point `AddPigeonWatch(IConfiguration)`. DbContext registration (SQL Server, `EnableRetryOnFailure`, upper-snake-case migrations history), ProblemDetails and the exception handler. The `IEndpointRouteBuilder` extension class with `MapPigeonWatch()`, which maps the filtered Identity endpoints, because the Host may not name `Data` types. | Business logic, controllers. |
| `BusinessLogic` | Services and providers. Depends on repository interfaces from `Data` and on `BusinessObjects`. | EF Core, ASP.NET, `WebApi`, `DependencyInjection`, `WebApi.Host`, DI registration code. |
| `Data` | `PigeonWatchDbContext`, internal EF entities, conventions, auditing, repositories and their interfaces, entity-to-BO mappers, migrations. | `BusinessLogic`, `WebApi`, `DependencyInjection`, `WebApi.Host`, DI registration code, public entities. |
| `BusinessObjects` | Plain domain and result types shared across layers. | Any other PigeonWatch project, EF Core, ASP.NET. |

Reference direction: `WebApi.Host -> {WebApi, DependencyInjection}`; `DependencyInjection -> {WebApi, BusinessLogic, Data, BusinessObjects}`; `WebApi -> {BusinessLogic, BusinessObjects}`; `BusinessLogic -> {Data, BusinessObjects}`; `Data -> BusinessObjects`.

Registration: only `DependencyInjection` registers services (`IServiceCollection` APIs). No other layer wires itself; `WebApi.Host` only calls `AddPigeonWatch` and `MapPigeonWatch` plus framework setup.

Data flow: a repository in `Data` loads an entity and maps it to a business object through a `Data/Mappers` mapper, so entities never leave `Data`; a service in `BusinessLogic` works on business objects; a controller in `WebApi` calls the service and turns the business object into an API model through a view model creator. Controllers return only API models, never business objects or entities.

Folder and namespace conventions:

- Controllers (types deriving from `ControllerBase`): `WebApi/Controllers/` (`PigeonWatch.WebApi.Controllers`). Every public action returns exactly `Task<ActionResult<T>>` with `T` from `PigeonWatch.WebApi.Models`. One exception, for binary responses: an action may return `Task<ActionResult>` when it carries `[Produces]` naming a single `image/*` content type (today `GET sightings/{id}/photo` and `GET sightings/{id}/photo/thumbnail`, which return `File(stream, "image/jpeg")`); `ControllerActionTests` enforces both rules.
- API models (types ending in `Model`): `WebApi/Models/`.
- View model creators: `WebApi/ViewModelCreators/`. Request-model mappers: `WebApi/Mappers/`.
- Services: `BusinessLogic/Services/`.
- Repositories: `Data/Repositories/`. Entity-to-BO mappers: `Data/Mappers/`. Entities: `Data/Entities/` (internal). Migrations: `Data/Migrations/`.
- Interfaces: an `Interfaces/` subfolder of the folder that holds their implementations (`BusinessLogic/Services/Interfaces/IAccountService.cs`, `Data/Repositories/Interfaces/IAccountRepository.cs`, `WebApi/ViewModelCreators/Interfaces/…`). The namespace stays the parent folder's namespace (`PigeonWatch.BusinessLogic.Services`, not `….Services.Interfaces`), so consumers need no extra `using`. An `Interfaces/` folder contains only interfaces.

The architecture tests in `ArchitectureTests/` enforce the layer dependencies, the registration rule, the folder and namespace conventions (including `Interfaces/` folders, checked by scanning the source files, since the namespace does not show the folder), the controller return type, internal entities, and the coding rules below that the build does not check (static classes, interfaces and registration, cancellation tokens, SQL naming, primary keys, audit columns). A violation fails `dotnet test`; the failure message lists the offending types. Run them with:

```
dotnet test PigeonWatch/Api/ArchitectureTests/PigeonWatch.ArchitectureTests.csproj
```

Known limits of the architecture tests: only classes deriving from `ControllerBase` count as controllers, so do not write POCO or `[Controller]`-attributed controllers. The interface-name rule accepts `I` plus any PascalCase suffix of the type name (so `SystemCurrentUserProvider : ICurrentUserProvider` passes), which means a bare `IService` or `IRepository` would also pass; always name the interface after the full role.

## Coding rules

- No `var`; every local declares its type explicitly (generated migration code is exempt).
- No static classes, except classes that only hold `const` values and the `IServiceCollection` or `IEndpointRouteBuilder` extension classes in `DependencyInjection` (the `StaticClassTests` allow-list). An extension class contains only extension methods: no private helpers, fields or nested types; inline lambdas are fine. Static members on non-static classes are allowed, so a `static readonly` lookup set lives in the non-static class that uses it.
- Classes with constructor dependencies use primary constructors.
- Methods and local functions have block bodies (`{ return …; }`), never expression bodies (`=> …`). This covers one-line methods, mappers, view model creators and test helpers too. Lambdas passed as arguments (`.Select(x => …)`, `AddEndpointFilter(async (context, next) => …)`) are not methods and stay lambdas; expression-bodied properties are not covered by this rule.
- Private fields are camelCase with no `_` prefix.
- Every `if` and `return` statement is preceded by a blank line, unless it is the first statement of its enclosing block or body (method, constructor, accessor, lambda, `if`/`else` or loop body).
- Interface members (methods and properties) are written without blank lines between them. Implementing classes separate methods with a blank line.
- An `if`, `else`, `for`, `foreach` or `while` body that is a single statement on one line has no braces. A body with more than one statement, or a single statement wrapped over several lines, keeps its braces.

  ```csharp
  UserAccountEntity? entity = await db.UserAccounts.FindAsync([id], cancellationToken);

  if (entity is null)
      return null;

  ApplicationUser user = userAccountMapper.ToUser(entity);

  return user;
  ```
- Every service, provider, repository, view model creator and mapper has a matching interface (`I<TypeName>`), is registered in `DependencyInjection`, and consumers depend on the interface. A strategy implementation may prefix the interface name (`SystemCurrentUserProvider : ICurrentUserProvider`). The interface file goes in the `Interfaces/` subfolder next to the implementation and keeps the implementation's namespace (see "Folder and namespace conventions").
- Every async method takes a `CancellationToken cancellationToken = default` parameter (interface declarations included). Controller actions are the only exception: they take `CancellationToken cancellationToken` without a default, bound by MVC to the request. Lambdas passed to framework APIs are not methods and are exempt.
- Every SQL identifier the application owns (tables, views, columns, keys, foreign keys, indexes, including EF's migrations history table `EF_MIGRATIONS_HISTORY` and its `MIGRATION_ID`/`PRODUCT_VERSION` columns) is UPPER_SNAKE_CASE. C# names stay PascalCase; the model-wide `UpperSnakeCaseNamingConvention` in `Data` derives the SQL names, so entities do not map names by hand. Table and view names are singular (`USER_ACCOUNT`, not `USER_ACCOUNTS`), so map each entity with a singular `ToTable` name. The database name (`PigeonWatch`, `pigeonwatch-db`) is exempt.
- Every entity derives from `AuditableEntity` and so carries the audit columns `CREATE_USER`, `CREATE_DATE`, `UPDATE_USER`, `UPDATE_DATE` (all NOT NULL, dates UTC `datetime2`, users `nvarchar(128)`). `AuditSaveChangesInterceptor` fills them on every save: an insert sets all four from the current user and time, an update sets only `UPDATE_*` and never changes `CREATE_*`. The user comes from `ICurrentUserProvider`, implemented by `HttpContextCurrentUserProvider`: the authenticated user's id (`ClaimTypes.NameIdentifier`), never the email, or `SYSTEM` for anonymous saves; time comes from the injected `TimeProvider`. Repositories never set audit columns themselves.
- Every table's primary key is a single `ID` column of type `UNIQUEIDENTIFIER`: entities inherit `Guid Id` from the internal abstract `Entity` base (which `AuditableEntity` derives from). Values are generated by EF on insert as sequential GUIDs (EF Core's default for `Guid` keys on SQL Server), which keeps the clustered index from fragmenting; code never assigns `Id` by hand.
- No comments in code.

The `var`, primary-constructor, block-body and field-naming rules fail the build (`.editorconfig` + `EnforceCodeStyleInBuild` in `Directory.Build.props`, which also covers the test project). The blank-line and brace rules are not checked by the build or the tests; follow them by hand. The other rules are enforced by the architecture tests.

## UI labels

- Every UI text the SPA shows is a key in `BusinessObjects/Resources/UiLabels.resx` (English, the neutral culture). Never hardcode UI text in the SPA; add a key here instead. The SPA bundles snapshots generated from these files and fetches `GET resources/{culture}` at runtime.
- Keys are lowercase dot paths: `<area>.<group>.<name>` in camelCase segments (`common.appName`, `auth.login.title`, `auth.errors.invalidCredentials`, `warmup.messages.1`). Values use positional placeholders only (`{0}`, `{1}`), no ICU or plural syntax.
- The resx is an embedded resource with no designer class, read through `ResourceManager` with `UiResources.BaseName`. `UiResourceService` serves `en` for an unknown, unsupported or malformed culture, and falls back to English per key.
- A new culture is added as `UiLabels.<culture>.resx` next to the neutral file (for example `UiLabels.pl.resx`); it becomes supported as soon as its satellite assembly exists, and missing keys fall back to English.
- API-side texts (ProblemDetails titles, Identity error descriptions) stay English diagnostics; the SPA maps error codes to label keys.

## Commands

Run from the repo root:

```
dotnet build PigeonWatch/Api/PigeonWatchApi.slnx
dotnet run --project PigeonWatch/Api/WebApi.Host/PigeonWatch.WebApi.Host.csproj
dotnet test PigeonWatch/Api/ArchitectureTests/PigeonWatch.ArchitectureTests.csproj   # architecture tests
dotnet test PigeonWatch/Api/UnitTests/PigeonWatch.UnitTests.csproj   # unit tests
dotnet test PigeonWatch/Api/IntegrationTests/PigeonWatch.IntegrationTests.csproj   # integration tests (real pipeline, SQLite in-memory)
dotnet list PigeonWatch/Api/WebApi.Host/PigeonWatch.WebApi.Host.csproj package --vulnerable --include-transitive   # dependency audit
dotnet list PigeonWatch/Api/ArchitectureTests/PigeonWatch.ArchitectureTests.csproj package --vulnerable --include-transitive   # test project dependency audit
dotnet list PigeonWatch/Api/IntegrationTests/PigeonWatch.IntegrationTests.csproj package --vulnerable --include-transitive   # integration test project dependency audit
dotnet tool restore   # pins dotnet-ef
dotnet ef migrations add <Name> --project PigeonWatch/Api/Data/PigeonWatch.Data.csproj --startup-project PigeonWatch/Api/WebApi.Host/PigeonWatch.WebApi.Host.csproj --output-dir Migrations
dotnet ef migrations has-pending-model-changes --project PigeonWatch/Api/Data/PigeonWatch.Data.csproj --startup-project PigeonWatch/Api/WebApi.Host/PigeonWatch.WebApi.Host.csproj
dotnet ef database update --project PigeonWatch/Api/Data/PigeonWatch.Data.csproj --startup-project PigeonWatch/Api/WebApi.Host/PigeonWatch.WebApi.Host.csproj   # applies to LocalDB
```

Local development uses SQL LocalDB (`PigeonWatch` database); the `ConnectionStrings:Default` value lives in user-secrets on the `WebApi.Host` project, not in the repo.
