# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Scope: `PigeonWatch/Frontend/` only — the Angular app. See `@PigeonWatch/CLAUDE.md` for what PigeonWatch is and how Api/Frontend fit together.

## What this owns

Angular 22 app (standalone components, SCSS, routing enabled, no SSR). Consumes the `Api/` project over HTTP — there is no shared build or repo-root package manifest between them.

Cross-cutting plumbing lives in `src/app/core/` (`auth/` token store, session, auth interceptor and guards; `configuration/`; `geolocation/` the geolocation service; `error-reporting/` the `ErrorReportingService` and the global error handlers; `warmup/` state and interceptor; `resources/` UI labels and the `translate` pipe; `http/` context tokens), lazy-loaded pages in `src/app/features/` (`sightings/` holds the map home, the sighting list, report form, detail page, My sightings, the API client, the wire types and the error mapping, plus `sightings/shared/` for components several sightings views use), shared UI in `src/app/shared/` (`ui/`, `map/`, and `http/problem-details.ts` for reading error codes and extensions from a ProblemDetails body), and global styles in `src/styles/`. Unit tests run on Vitest with jsdom through the `@angular/build:unit-test` builder (`test` target in `angular.json`); specs sit next to the code they cover as `*.spec.ts`. The schematics still default to `skipTests`, so add a `*.spec.ts` by hand when a component or service needs one. The `frontend-build-and-test` job in `.github/workflows/api-pr-checks.yml` runs the production build and the tests on every PR to `main`.

## UI library, styling and reusable components

These rules apply to every UI change. They were introduced by the `register-and-login` change (S-01).

- **Component library: Angular Material** (`@angular/material` + `@angular/cdk`, MIT, kept on the same minor as `@angular/core`). Use its primitives (`mat-form-field` + `matInput`, `mat-button`/`mat-flat-button`, `mat-card`, …) instead of hand-rolled equivalents. Import Material modules per component; there is no shared "material module". `matInput` binds to Signal Forms directly, so no `ControlValueAccessor` glue.
- **Never run `ng add @angular/material`** and never add web-font or icon-font `<link>`s: the CSP in `public/staticwebapp.config.json` allows only `'self'` fonts and stylesheets. Typography uses the system font stack; an icon font, if one is ever needed, is self-hosted.
- **No PrimeNG.** v22 uses the key-based PrimeUI license, not MIT. Also no Tailwind/Bootstrap.
- **Design tokens** live in `src/styles/_tokens.scss` as `--pw-*` CSS custom properties on `:root`: colors, spacing scale (`--pw-space-1…8`), typography, radii, border width, shadows, layout widths, control height, motion and z-index. Large-screen values switch on from `xl` inside `_tokens.scss` itself (`--pw-form-max-width` grows from 28rem to `--pw-form-max-width-xl`, and the map height follows `--pw-map-height-xl`). Raw color and length values may appear only in `_tokens.scss`, `_material-theme.scss` and `_breakpoints.scss`. Need a new value? Add a token, don't inline it.
- **Material theme** lives in `src/styles/_material-theme.scss` (`mat.theme` + `mat.theme-overrides`) and maps our tokens onto Material's `--mat-sys-*` system tokens. Per-component tweaks use `mat.<component>-overrides(...)` there, never CSS that targets `.mat-*` / `.mdc-*` classes. The header user button's pressed state and open shape are keyed there on `button.app-header__user-button` (the element selector outranks Material's own rule). One accepted exception: the menu and select overlay panels (`.pw-user-menu-panel`, `.pw-select-panel` in `_common.scss`) repeat their class (`.x.x`) to outrank Material's panel rules, because the overrides API has no border or margin keys for them. The keyboard focus ring on Material buttons comes from `mat.strong-focus-indicators` in the same file, pointed at the `--pw-focus-*` tokens, because Material buttons hide the global `:focus-visible` outline.
- **Common classes** live in `src/styles/_common.scss` (`pw-` prefix, built from tokens only) for what Material doesn't style: layout (`pw-container`, `pw-stack`, `pw-cluster`, `pw-center-screen`, `pw-full-width`), typography (`pw-title`, `pw-subtitle`, `pw-text-muted`, `pw-text-small`) and `pw-visually-hidden`. `src/styles.scss` only `@use`s tokens → material-theme → base → common. Breakpoints are SCSS (`@use 'breakpoints'` → `@include from(md)`), because media queries can't read custom properties.
- **Component stylesheets** use `var(--pw-*)` and `pw-*` classes only: no color/length literals, no `style="…"` in templates, no `::ng-deep`, no `!important`, no `.mat-*` / `.mdc-*` selectors, and no redefining a `pw-*` class. `src/styles/style-token-coverage.spec.ts` enforces this.
- **Reusable app components** live in `src/app/shared/ui/` (exported from `index.ts`): `app-page-card` (title, optional subtitle, a `headerActions` slot beside the title, actions slot, and a `width` input, `form` or `wide`: `wide` grows the card to `--pw-page-card-wide-max-width` from `xl` and behaves like `form` below it; the footer collapses when nothing is projected; the `h1` has `tabindex="-1"` and `focusHeading()` moves focus to it), `app-alert`, `app-field-errors`, `app-submit-button` (`busy`, `disabled` and a `tone` input, `primary` or `success`), `app-form-actions` (the Cancel + submit pair, laid out in one place; below `sm` it stacks with the submit on top while DOM and Tab order stay Cancel, submit — an accepted exception, see impl-review F1), `app-brand` (logo mark + app name, `md`/`lg`), `app-loading-indicator` (the spinner with its accessible `label`; `layout` `block` or `inline`; `live` gives the host `role="status"`, turn it off inside an existing live region), `app-error-retry` (projected error message in an `alert` plus a natural-width retry button; `retryLabel` input, `retry` output), `dl[app-detail-list]` with `div[app-detail-item]` (label/value rows; list `layout` `column` or `inline`, item `label` and `value` `plain`, `text` or `numeric`) and `app-criticality-badge` (`kind` from `MapMarkerKind`, a token-coloured dot plus the projected label). `app-error-reference` (input `traceId`; renders nothing without one, otherwise the `common.errorReference` label, "Reference: {0}") sits inside the unexpected-error alerts. They're standalone and OnPush with signal inputs, carry no literal text or resource keys of their own (callers pass translated text or project content) except `app-error-reference`, the one `shared/ui` component that translates its own label, and expose variations as inputs. Check `shared/ui` before writing markup in a feature. When a pattern shows up in a second feature, promote it to `shared/ui` in the same change instead of copying it.
- **Feature-shared sightings components** live in `src/app/features/sightings/shared/` (no barrel, imported by file path). They are the one exception to the `shared/ui` promotion rule: they may use `sighting.types` and resource keys, which `shared/ui` forbids, so they stay inside the feature. `app-sighting-filters` (class `SightingFilterRow`; inputs `statusOptions` (required), `initial`, applied as the starting selection and not emitted, and `disabled`; output `filtersChange`) is the status and criticality filter row: the map offers `filterableSightingStatuses` (five open statuses), the list `allSightingStatuses` (all nine). `li[app-sighting-row]` (inputs `sighting` and `now`) is one sighting in a list, used by My sightings and the sighting list: the whole row is one link to the detail page (hover highlight, the global focus ring around the row; the list itself has no gap, the row's padding spaces it), holding the bold name (or `sighting.unnamed`, not styled as a link), status, criticality badge and a relative age from `sighting-age.ts` (`sighting.age.*` keys, abbreviated units, no plural syntax) in a `<time>` whose `datetime` is `createdAt` and whose `title` is the absolute medium date. When `hasPhoto` is true the row starts with a `--pw-row-thumb-size` (3rem) square beside the text column (name and meta) and the name carries the visually hidden label `sighting.row.hasPhoto`, so the row link's accessible name says the sighting has a photo; rows without a photo reserve no square. The square shows the inline SVG camera glyph (`aria-hidden`, `focusable="false"`, `currentColor`, sized by `--pw-row-icon-size`) until the thumbnail has loaded and again when it fails, and then the thumbnail as a decorative `<img alt="">` with `object-fit: cover`; see "Sighting photos". The parent passes one `now` captured when its data loaded, so a list renders against one clock and specs are deterministic.
- **Sighting list** (`features/sightings/sighting-list-page/`, route `sightings/list`, declared before `sightings/:id`, guarded, `layout: 'wide'` so the wide card can grow past `--pw-content-max-width` on large screens). A wide `app-page-card` titled with the total match count once a page has loaded (`list.page.titleWithCount`, plain `list.page.title` before that), with a "Map view" header link (`routerLink="/"` carrying the list's current filters as `{ mapFilters }` state, which the map restores), the filters behind a toggle like the map's (`map.filters.show`/`showActive`/`hide`), rows and a pager (hidden while `totalCount` is 0). The pager is one row from the `md` width of its own container (`bp.container-from(md)` in `_breakpoints.scss`, a container query because the card width, not the viewport, decides): the page-size `mat-select` (`sightingListPageSizes` 10/20/30) on the left, the page number as `list.paginator.range` ("current / last") in the centre and a `mat-paginator` with `hidePageSize` for the first/previous/next/last buttons on the right; narrower, the page size takes its own right-aligned row above the number and the buttons. Pages load through `SightingsApi.list` (`POST sightings/list`) in a `switchMap` pipeline; a filter or page-size change goes back to page 1, and a later page that comes back empty while `totalCount` is above 0 asks once for the last page, and for page 1 if the last page comes back empty as well. Page, page size and filters live only in the page, so every visit starts at page 1. Each row link (the row's `linkState` input) carries `{ returnToList: { centre, filters } }` as navigation state; the sighting detail page reads it through `readSightingDetailReturn` (the same guard as the map's hand-over) and then shows "Back to list" (`sighting.detail.backToList`, `routerLink="/sightings/list"` with that hand-over as state, so the list reopens at the same centre and filters on page 1) instead of "Back to map"; without valid state (from the map, My sightings, a reload or a pasted URL) it keeps "Back to map". The centre comes from the map's hand-over or, without one, from `GeolocationService.currentPosition(false)`; any failure shows `list.page.locationUnavailable` with a link to the map and sends no request. An unexpected failure renders `app-error-retry` with `app-error-reference` and reports `sightings.list`; a 400 counts as unexpected here, because the page sends no user-typed input, so it is reported and shows its reference. The page provides `SightingListPaginatorIntl`, a `MatPaginatorIntl` that reads the button labels (`list.paginator.*`) from `ResourceService` and returns an empty range label (the page renders its own), so Material's English labels never show; a future paginator elsewhere provides the same kind of intl.
- **Spinners, errors with retry, label/value lists and criticality have one implementation each.** Features render loading through `app-loading-indicator`, never `mat-progress-spinner` directly (`style-token-coverage.spec.ts` fails on a `<mat-progress-spinner` in any template outside `src/app/shared/ui/`), an error with a retry through `app-error-retry` (one exception: the map home puts its Try again in the toolbar beside "Search this area" and its error `app-alert` inside the toolbar's status slot beside the status element, because one component cannot span both), and label/value pairs through `app-detail-list`. Criticality is never shown as plain text or as colour alone: wherever a sighting's criticality appears (cards, lists, legends), it is an `app-criticality-badge`.
- **Route width.** The shell caps `<main>` at `--pw-content-max-width` (40rem). A route whose page needs more room declares `data: { layout: 'wide' }` (the map home, the report page and the sighting detail page); `app.ts` reads it from the active route after each navigation and adds `app-main--wide`, which from `md` uses `--pw-content-wide-max-width` (64rem) and from `xl` (1280px) `--pw-content-wide-xl-max-width` (90rem). A `'roomy'` value (`app-main--roomy`: 40rem, 64rem from `xl`) is supported by the shell but no route uses it. The header bar follows the `wide` tiers on every route, so its contents never move between pages. Use the route flag, not a page-level width override; routes without a flag, such as profile, login and register, stay at 40rem.
- **Arrival and secondary navigation.** A routed view that needs to announce itself sets its own tab title through `Title` (a resx key composed with `common.appName`), resets it to `common.appName` on destroy, and calls `PageCard.focusHeading()` through `afterNextRender` once its state leaves loading; the first-arrival focus runs only when the page was created by a router navigation, so the kitchen sink never takes focus on load. Only the sighting detail page does this today: no route sets `title`, and app-wide route titles and focus on navigation are not built. A card page's secondary navigation link (Back, Create account) goes in the card's `actions` slot, not in a wrapper above the card.
- **A variant is a component input, never a global class.** A different look of a shared component (the green Save is `<app-submit-button tone="success">`) is an input on that component, reflected as a host attribute and keyed in `_material-theme.scss` through `mat.<component>-overrides(...)`. A global `pw-button-*`-style class is not allowed: `style-token-coverage.spec.ts` fails when a template uses a `pw-*` class that `_common.scss` does not declare, or contains a colour literal or an inline `style`.
- **Kitchen sink** lives in `src/app/dev/kitchen-sink` and is served at the `dev/kitchen-sink` route in development builds only (`npm start`, no API and no login: every cell runs its own stubbed services). `dev/dev-routes.ts` is swapped for an empty route list through `fileReplacements` in the production configuration, so nothing of it reaches `dist/`. The route declares the wide layout so the Nearby map and Sighting detail cells render at the wide tier (90rem from `xl`), while the Profile group keeps `--pw-content-max-width`. Cells are grouped by view: **Profile** (the page, the password dialog, and one cell with My sightings items with relative ages) and **Nearby map** (locating, zoomed out with Search disabled, the zoom-10 hint, "Locate me" with the next answer chosen in the cell header, retry locating, first and repeated loading, found, selected by pointer and by keyboard, empty, nearby error, nearby error after a denied location, map library failed, map library failed with the position unknown) and **Sighting detail** (`detail-*` cells: loaded, unnamed, long name, map shown, not found, error, loading, error then loaded, map library failed after "Show map", and the photo cells `detail-photo-loaded`, `detail-photo-loading` and `detail-photo-error`; the error-then-loaded retry runs from a `manual` header button because the retry moves focus to the heading) and **Sighting list** (`list-*` cells at the narrow width: locating, location denied, loading, loaded with mixed criticalities and ages, `list-thumbnails-loading` and `list-thumbnails-error` (photo rows keep the camera icon), second page reached through Next page, empty, a filter with no match chosen from the cell header, and error; the cells use the geolocation stub, never a hand-over). A `CellDefinition` names its `group` and the stub modes of its cell. `CellStubs` (provided per cell in `state-cell.ts`) stubs `SessionService`, `ConfigurationService`, `ProfileApi`, `SightingsApi` (`mine()` empty or with items; `nearby()` items, empty, failure, pending, or items then pending; `get()` loaded, unnamed, long name, loaded with a photo, 404, 500, pending, or a 500 then loaded; `photo()` a generated 4:3 SVG image, pending or a 500, chosen by the cell's optional `photo` mode; `photoThumbnail()` the same image, pending or a 500, chosen by a list cell's optional `thumbnail` mode (every other cell, My sightings included, gets the image); `list()` items, paged over 13 fixtures, empty, failure or pending, filtered and sliced by the request; some list and My sightings fixtures carry `hasPhoto` so rows show a thumbnail) and `GeolocationService` (ok, denied, timeout, pending, or timeout then a chosen answer), and wraps `LEAFLET_LOADER` either with a tile-less Leaflet (`tileLayer` replaced by an empty grid layer, so real focusable markers render and no request reaches `tile.openstreetmap.org`) or with a loader that fails. Cells reach their state through the real DOM with `cell-driver.ts` steps that run on load; a scenario that moves focus (selecting a marker focuses the card heading) runs from a `manual` button in the cell header instead, so the sink never scrolls or takes focus on load. A new state of the Profile page, the password dialog, the map home, the sighting detail page or the sighting list (or a change that adds one) needs a cell in `cell-definitions.ts` and a marker assertion in `kitchen-sink.spec.ts`, which swaps `MapView` for `MapViewStub` on `NearbyMapPage` and `SightingDetailPage` and provides a `PhotoEncoder` stub for the object-URL helpers, because jsdom has no `URL.createObjectURL`. A new data dependency on any of these pages needs a stub mode in `CellStubs` and the same stub in that page's own spec. It is the one place with literal English text (state labels, action names), because the page never ships and production UI text rules do not apply to it. The visual evidence lives in `context/archive/2026-10-11-profile-ui-contract/visual-notes.md` (Profile), `context/archive/2026-10-11-nearby-map-ui-contract/visual-notes.md` (nearby map) and `context/changes/sighting-detail-ui-contract/visual-notes.md` (sighting detail; under `context/archive/` once the change is archived).
- **Form fields are outlined** with dynamic subscript sizing, and **validation errors show on submit, not on blur**. A component that uses `mat-form-field` adds `providers: [provideFormFieldDefaults()]` (from `shared/ui`) and calls `inject(FormSubmitState).markSubmitted()` at the start of its submit handler instead of `markAsTouched()`. The provider brings a page-scoped `FormSubmitState` and a `SubmitErrorStateMatcher`, so the red outline and the `app-field-errors` message both appear only once the form has been submitted, then follow edits live. It is not provided in `app.config.ts`, because that would pull Material form-field into the initial bundle.
- **Initial-bundle code imports `shared/ui` by file path.** `app.ts` and everything under `core/` import a component from its own file (`shared/ui/page-card/page-card`), never from `shared/ui/index.ts`: the barrel re-exports form-field and Signal Forms code, which would land in the main bundle and break the 500 kB initial budget. Lazy feature pages may use the barrel. The initial bundle was last measured at 529.9 kB after `sighting-row-photo-thumbnail` (about 10.1 kB under the warning; 529.4 kB after `attach-sighting-photo`; 527.8 kB after `urgency-ranked-sighting-list`, which raised the warning limit in `angular.json` from 520 kB to 540 kB: the lazy list page's `mat-paginator` adds about 10 kB to the initial chunk, because its icon-button and tooltip code lives in Material and CDK files the initial chunk already loads and esbuild keeps a whole file in one chunk (516.3 kB after `filter-sightings-nearby`; 512.1 kB after `app-wide-large-screen-layout`, which raised the limit from 500 kB to 520 kB for `mat-select` and the menu theming)). Check `npm run build` against the budget whenever initial-bundle code changes.

## Maps and geolocation

Introduced by the `report-sighting-on-map` change (S-03).

- **Leaflet 1.9.4** (`leaflet` + `@types/leaflet`, raster tiles from OpenStreetMap). It is CommonJS, so `angular.json` lists it in `allowedCommonJsDependencies`; its CSS is a non-injected `styles` bundle (`inject: false`, emitted unhashed as `leaflet.css`), which the default `LEAFLET_LOADER` in `map-view` adds as a `<link>` on first use, so no part of Leaflet is in the initial bundle. Markers are `divIcon`s; there are no marker image files.
- **Map code lives in `src/app/shared/map/`**: `map-view/` (`app-map-view`, the only file that imports Leaflet, loading it with `from(import('leaflet'))`), `location-picker/`, `map-config.ts` (tile URL, attribution link, zoom limits, the neutral Poland view, the default zooms and `minSearchZoom`), `map-marker.ts` (marker type and class names) and `testing/map-view-stub.ts`. It has no barrel and is **not exported from `shared/ui/index.ts`**: lazy feature pages import it by file path, so Leaflet and the adapter land only in the chunks that render a map, never in the initial bundle or in pages that merely use the `shared/ui` barrel. `core/` and `app.ts` never import it.
- **Never pass user text into Leaflet HTML.** Popups, tooltips and `divIcon` `html` parse strings as HTML. Marker icons use static class names only (`pw-map-marker` plus a criticality modifier, declared in `_common.scss` from the `--pw-color-criticality-*` and `--pw-map-*` tokens), and selecting a marker shows an Angular-rendered card in the map page's aside instead of a popup. The attribution text is escaped in `map-config.ts`.
- **`app-map-view` API.** Inputs `label`, `center`, `zoom`, `markers`, `pin`, `selectedId` and `interactiveMarkers` (default `true`; the matching marker gets `pw-map-marker--selected` and a raised z-index, and every marker carries `aria-pressed` unless `interactiveMarkers` is `false`); outputs `mapClick`, `centerChange` and `zoomChange` (both on `moveend`), `markerSelect`, `pinMove`, `mapReady` and `loadFailed` (`true` each time Leaflet fails to load, `false` when a retry starts after a failure, no emission on a first successful load; the location picker and the detail map ignore it); method `focusMarker(id)`. A `ResizeObserver` on the canvas (skipped where it is undefined, as in jsdom) calls `invalidateSize` when the container changes size and is disconnected on destroy. Markers are keyboard-operable: Tab reaches them, and Enter or Space emits `markerSelect` like a click (Space does not scroll the page). A page that shows details for a marker passes the selection back through `selectedId`, puts the criticality in the marker `label` (`map.markerLabel`), moves focus to the details on select, and calls `focusMarker` when they close. The location picker leaves `selectedId` `null`. The detail map passes `[interactiveMarkers]="false"`: its one marker is a plain visual with no Tab stop, no `role="button"`, no `aria-pressed` and no `markerSelect`, and still carries the criticality in its `title` through `map.markerLabel`. Display-only icons also get `pw-map-marker--static` (declared in `_common.scss`) so Leaflet's pointer cursor does not suggest a click.
- **CSP**: `public/staticwebapp.config.json` admits exactly one external host, `img-src https://tile.openstreetmap.org`, which widens a policy that protects the `localStorage` refresh token. The full line is `img-src 'self' data: blob: https://tile.openstreetmap.org`: `blob:` was added by `attach-sighting-photo` so the photo preview and the detail photo can render from object URLs our own scripts create (a deliberate trade-off; `map-config.spec.ts` asserts the line). A tile provider change touches `map-config.ts` and that one CSP line, nothing else. The CSP is applied by the Static Web Apps edge, so `ng serve` cannot verify it: after any change to the CSP, the tile host or how the map loads, check the production build served with those headers (for example the Static Web Apps CLI emulator) or the deployed site, with the console and network panel open, for tiles loading and no CSP violations.
- **Cost guardrail**: render a map only where the page is about the map. The detail page shows coordinates as text and creates its map only behind the "Show map" toggle, so no tile is fetched until it is pressed.
- **Pin-picker**: `app-location-picker` is the repo's first custom Signal Forms control (`FormValueControl<GeoPoint | null>`), bound with `[formField]` like a native input. Tapping the map places or moves the pin, the pin is draggable, "Use my location" fills it from geolocation, and "Place pin at map centre" is the non-pointer path; the chosen coordinates show as text. Its required error renders through `app-field-errors` gated by `FormSubmitState`, so the host page needs `provideFormFieldDefaults()` like any other form.
- **Geolocation**: `core/geolocation/geolocation.service.ts` is the only caller of `navigator.geolocation`. `currentPosition(highAccuracy)` returns an Observable that emits once and never errors: `{ status: 'ok', latitude, longitude }` or `denied`, `unavailable`, `timeout` (10 s, always set) or `unsupported` (no `navigator.geolocation`, as in jsdom). The map home asks with low accuracy, the picker with high accuracy. Without a position the map opens on the neutral Poland view and waits for "Search this area", which stays disabled while the zoom is below `minSearchZoom` (10), a search is loading or the position is being located (with `disabledInteractive`, so it stays focusable, and the reason in the status line). After `denied`, `unavailable` or `timeout` (not `unsupported`) the map home shows a "Locate me" button (`map.locateMe`; the picker keeps "Use my location", `map.useMyLocation`) that asks again with low accuracy; only the latest request may move the map. While the map has failed to load (`loadFailed`), the map home drops the result, hint and zoom statuses and disables Search; the locating and loading statuses and the error alert stay. Nearby is 10 km around the map centre, applied by the API (`GET sightings/nearby`); the SPA reads `clientConfig.sightingRules.nearbyRadiusKm` only to show it in text.
- **Nearby filters** (introduced by `filter-sightings-nearby`, S-05). The map home narrows the search by status (the five open statuses) and criticality, sent as repeated `statuses` and `criticalities` query parameters on `GET sightings/nearby`; the API applies them before its 200-row cap. A "Show filters" toolbar toggle (`nearby-filters-toggle`, `aria-controls` and `aria-expanded`; "Show filters (N)" when N values are chosen, "Hide filters" while open and highlighted through `_material-theme.scss` and `--pw-color-info-surface`) opens `app-sighting-filters` below the toolbar: two multi-select `mat-select` fields with an "All" placeholder and a "Clear filters" button. The row is hidden, not destroyed, when collapsed, so choices persist while the page lives. An empty selection means no filter. A filter change re-runs the search at the last search centre and clears the selection, as "Search this area" does; before the first search, while zoomed out below `minSearchZoom` or while the map failed to load, it only stores the filters. An empty result with an active filter shows `map.filters.noMatch` instead of `map.empty`. The filter state is not in a service, the URL or storage; it lives in the page and in router navigation state, so a fresh visit (the home link, a reload, a bookmark) starts without filters. It leaves the page through the "List view" toolbar link (`map.listView`): after a search has run, it passes `{ centre: lastSearchCentre, filters }` (`SightingListHandOver` in `sighting-list-page/sighting-list-hand-over.ts`) as router navigation state, and before a search it passes none. The list reads it from `Router.currentNavigation()?.extras.state` through `readSightingListHandOver`, a type guard that treats the state as untrusted input (finite latitude in [-90, 90], longitude in [-180, 180], known status and criticality values; any of the nine statuses) and otherwise behaves as if opened directly. The hand-over lives in the history entry, so Back from a sighting detail restores the centre and filters (on page 1), while a reload in a new tab or a bookmark falls back to geolocation. It comes back to the map three ways, all read through `readNearbyMapFilters` (the same filter guard, keeping only the five open statuses because nearby rejects resolved ones): the list's "Map view" and "Open the map" links pass `{ mapFilters }` (`NearbyMapReturn`) with the list's current filters; the selected card's "Open details" link passes the map's `{ mapFilters }` to the sighting detail page, whose "Back to map" hands them back (without them, from My sightings or a reload, it is a plain link); and every filter change on the map writes `mapFilters` into the map's own history entry (`Location.replaceState` with the existing state kept), so browser Back from the list restores them. The map starts with the restored filters in its first search and as the filter row's `initial` selection; the centre is not restored and still comes from geolocation. Kitchen-sink cells `map-filtered` and `map-filtered-no-match` cover the states, and `tests/e2e/nearby-filters.spec.ts` keeps a matching criticality filter showing a reported marker and a non-matching one removing it.
- **Stub the map in specs.** jsdom has no layout or canvas. Any spec that renders a component containing `app-map-view`, directly or through a routed page (as `core/auth/auth.guards.spec.ts` does for the home route), swaps it for the stub: `TestBed.overrideComponent(Host, { remove: { imports: [MapView] }, add: { imports: [MapViewStub] } })`. The stub has the same selector, inputs and outputs, so a spec reads `center()`/`zoom()`/`markers()`/`selectedId()` from it, emits `mapClick`, `centerChange`, `zoomChange`, `markerSelect` or `pinMove` to drive the page, and reads `focusMarker` calls from `focusedMarkers`. Component specs provide a `GeolocationService` stub returning the outcome under test; only `geolocation.service.spec.ts` fakes `navigator.geolocation`.

## Sighting photos

Introduced by the `attach-sighting-photo` change (S-04). The API contract is in `@PigeonWatch/Api/CLAUDE.md` ("Sighting photos").

- **`PhotoEncoder` seam** (`features/sightings/shared/photo-encoder.ts`, `providedIn: 'root'`, shared by the photo picker, the detail page and the sighting rows). `encode(file, maxDimension)` re-encodes in the browser: `createImageBitmap` with `imageOrientation: 'from-image'`, a canvas scaled so the longest edge is at most `photoMaxDimension`, then `toBlob('image/jpeg', 0.85)` (canvas output has no EXIF). A decode failure (for example HEIC in Chrome) is a `PhotoDecodeError`, which the picker shows as an unsupported type without a report; an out-of-memory rejection on a huge image looks the same (accepted, impl-review F8). A bitmap that finishes decoding after the encoding was cancelled is closed; a missing 2D context or empty output is a `PhotoEncodeError`. `createPreviewUrl(blob)` and `revokePreviewUrl(url)` wrap `URL.createObjectURL`/`revokeObjectURL`, so every page that shows a blob goes through it and specs stub it (jsdom has neither the canvas nor object URLs).
- **Photo picker** (`app-photo-picker`, `features/sightings/report-sighting-page/photo-picker/`) is a Signal Forms control (`FormValueControl<Blob | null>`) bound with `[formField]`, like the location picker. A visible "Choose photo" button opens a hidden file input (`accept` from `photoAllowedContentTypes`), the chosen file is encoded through `PhotoEncoder`, rejected above `photoMaxBytes`, previewed through an object URL that is revoked on change and on destroy, and removed with "Remove photo". The preview is left-aligned (`align-self: flex-start`), because `pw-stack` is a flex column that would stretch it. An unexpected encode failure reports `fallback` under `sighting.photo.encode`.
- **Create and errors.** `SightingsApi.create` sends `FormData` (no `Content-Type` set by hand) with a `photo.jpg` part only when there is a photo. The error codes are PascalCase: `PhotoTooLarge`, `PhotoUnsupportedType` and `PhotoUnreadable` become photo field errors and are not reported; there is no 413 mapping, because the API answers an over-limit body with 400 `PhotoTooLarge`. `PhotoStorageUnavailable` (503) is a form-level alert ("retry or remove the photo") with `app-error-reference`, reported, and the form keeps its values.
- **Warm-up exclusion.** The warm-up interceptor passes a 503 whose ProblemDetails `errors` contain `PhotoStorageUnavailable` straight through; every other 503 or status-0 answer keeps the cold-start retry.
- **Detail photo.** When `hasPhoto` is true, the sighting detail page loads `SightingsApi.photo(id)` (`responseType: 'blob'`, the bearer token rides on `HttpClient`, so an `<img src>` pointing at the API would not work) in its own stream, so the rest of the page never waits for it. While it loads, a square placeholder of `--pw-photo-thumb-size` (200 px) holds the loading indicator (`sighting.detail.photoLoading`); loaded, a square thumbnail of the same size shows the image with `sighting.detail.photoAlt` ("Photo of {0}", the page title), cropped to the centre with `object-fit: cover`, inside a `button` labelled `sighting.detail.photoOpen` that shows a pointer cursor, a slight zoom and an "Open the full photo" strip on hover and keyboard focus, and opens `PhotoDialog` (`sighting-detail-page/photo-dialog/`, a `MatDialog` with the sighting title, the uncropped image capped at `--pw-photo-dialog-max-height` and a Close button, `sighting.detail.photoClose`; opened with `autoFocus: 'dialog'` so focus lands on the dialog itself and the Close button shows no focus ring until the user tabs to it) sized by `--pw-photo-dialog-max-width`. The thumbnail sits beside the key facts (status, criticality, reporter, reported at), a wrapping row whose facts list is a grid of `--pw-detail-fact-min-width` columns, so the facts use two columns when there is no photo and drop below the photo on a narrow card; description, behaviour and location follow full width; a failure shows `sighting.detail.photoError` as an info `app-alert` and reports `api-failure` under `sighting.detail.photo`, except for the expected statuses of `isExpectedClientStatus` (400, 401, 429); a 404 is still reported, because `hasPhoto` promised a blob. The object URL is revoked when the route moves to another sighting, on a reload and on destroy. No request is sent when `hasPhoto` is false.
- **Row thumbnails** (`sighting-row-photo-thumbnail`). `li[app-sighting-row]` loads `SightingsApi.photoThumbnail(id)` (`GET sightings/{id}/photo/thumbnail`, a 160 px square the API creates at upload, `responseType: 'blob'`) only when `hasPhoto` is true and only once the row comes within 200px of the viewport: after the first render an `IntersectionObserver` on the host marks it visible once and disconnects (also on destroy), and where `IntersectionObserver` is undefined (jsdom) the row counts as visible at once. The blob becomes an object URL through `PhotoEncoder.createPreviewUrl` inside a `switchMap`, so the URL is revoked when the sighting changes and on destroy. A failure keeps the camera icon and reports `api-failure` under `sighting.row.photo`. The row therefore injects `SightingsApi`, `PhotoEncoder` and `ErrorReportingService`; a host spec that renders a photo row must stub `photoThumbnail` and `PhotoEncoder`.
- **Tests.** Page specs stub `PhotoEncoder` and `SightingsApi.photo`; `sighting-row.spec.ts` drives a fake `IntersectionObserver` through `vi.stubGlobal`; the kitchen-sink cells are listed under "Kitchen sink"; `tests/e2e/sighting-photo.spec.ts` reports a sighting with `tests/e2e/fixtures/pigeon.jpg` through the real form and API, checks the detail image has a non-zero natural width, and finds the loaded thumbnail (non-zero natural width, no camera icon) on its row in My sightings.

## Reporting errors

Introduced by the `spa-error-reporting-seam` change. The SPA posts a small report to `POST client-errors` (see `@PigeonWatch/Api/CLAUDE.md`) so failures that used to end silently in the browser reach the API log.

- **Report what the UI shows as unexpected.** A caught error that the UI turns into a generic or unexpected state, and a failure that is swallowed (a catch that falls back, a lazy chunk that does not load, a session that expires), goes through `ErrorReportingService.report(kind, context, error)` from `core/error-reporting`, never an empty catch or a bare `console` call. The unexpected-error states (nearby map, My sightings, sighting detail, report form, profile and the auth forms) also render `<app-error-reference [traceId]="...">` with `unexpectedTraceId(error)` from `shared/http/problem-details`, so a user can quote the reference.
- **Expected user conditions do not report.** A validation 400, an invalid-credential 401, a 404 miss, a 429 and the sighting cooldown are answers the UI already explains; `isExpectedClientStatus` names the statuses, and those states show no reference.
- **Contexts are lowercase dotted keys** (`nearby.search`) matching the pattern the API validates, and `kind` is one of `ErrorReportKind`. A new context is a plain string at the call site; no resx key, since it is never shown.
- **Never put user data in a report.** No messages, URLs, query strings, ids, tokens, emails or coordinates: the payload is a closed allowlist built by the service itself (`kind`, `context`, `httpStatus`, `errorName`, `traceId`, `route` as a template, `sessionId`), so a call site passes the error object and nothing else.
- **The reporter is bounded.** It dedupes on kind, context and status, sends at most 20 reports per page load, and a failed send only logs a console warning, so reporting can never loop or throw into the caller.
- **Tests.** The Playwright test `tests/e2e/error-reporting.spec.ts` forces a 500 on `sightings/nearby` and asserts the shown reference and the `POST client-errors` body; page specs assert report-or-silent per status.

## Registration during a cold start

Introduced by the `testing-cold-start-registration-resilience` change (test-plan Risk #1). The warm-up interceptor resends a register POST after status `0` or `503`, and nothing makes that resend idempotent, so a lost response for an account that was created would otherwise end in a false "couldn't create" message.

- **Resend token.** `REQUEST_RESENT` (`core/http/http-context-tokens.ts`, default `false`, same style as `AUTH_RETRIED`) is set on the request's `HttpContext` when the warm-up interceptor schedules its first resend. The interceptor stays generic; `AuthApi.register(request, context?)` lets the caller read the token afterwards.
- **Recovery rule.** `SessionService.register` recovers only after an inconclusive attempt: a 400 carrying `RegistrationFailed` while `REQUEST_RESENT` is set, or while the submitted email equals the in-memory unanswered email (trimmed, lowercased) left by an earlier register that ended with status `0` or `503` after the warm-up budget. It then makes one `login` with the typed credentials, and success is a normal sign-in. A failed recovery rethrows the original 400 (a `401` also clears the marker), and a recovery login that itself ends unanswered rethrows that transport error and keeps the marker. An ordinary duplicate sends no extra request. A taken display name also answers `RegistrationFailed` (the API no longer returns a display-name-specific code on register), so a resent register with a taken name makes the same single recovery login, which fails and rethrows the original 400. Only the email is remembered, never the password, and it is gone on reload.
- **Register-only message.** `registerFailure` maps status `0` and `503` to `registrationUnconfirmed` (`auth.errors.registrationUnconfirmed`: "We couldn't confirm whether your account was created…"), not to the generic warm-up text. `loginFailure`, `profileFailure` and `passwordChangeFailure` keep `warmupFailed`.
- **Tests.** `core/auth/register-cold-start.spec.ts` composes the real `authInterceptor`, `warmupInterceptor`, `AuthApi` and `SessionService.register` over `provideHttpClientTesting()` with fake timers; extend it for any change to this flow (cookbook: `context/foundation/test-plan.md` §6.2).

## UI text and resources

- **Every UI text is a key in `PigeonWatch/Api/BusinessObjects/Resources/UiLabels.resx`.** Templates and components contain no literal UI text: labels, buttons, messages, hints, validation and warm-up lines all come from that file. Need a new text? Add a key to the resx in the same change, not a string in the SPA.
- **Key format**: lowercase dot paths, `<area>.<group>.<name>` with camelCase segments (`common.appName`, `auth.login.title`, `auth.errors.invalidCredentials`, `warmup.messages.1`). Values use positional placeholders only (`{0}`, `{1}`); no ICU or plural syntax.
- **A new culture** is added as `UiLabels.<culture>.resx` next to the neutral English file (for example `UiLabels.pl.resx`). Missing keys fall back to English per key, and the API serves `en` for any culture without a resx.
- **Reading labels**: templates use the `translate` pipe (`{{ 'auth.login.title' | translate }}`, `{{ 'auth.validation.passwordMinLength' | translate: 8 }}`); code uses `ResourceService.translate(key, ...args)`. The API serves the map at `GET {apiUrl}/resources/{culture}`. `scripts/generate-resources.mjs` (run by `prestart`, `prebuild` and `pretest`) bundles every `UiLabels*.resx` into `src/app/core/resources/generated/` (gitignored), so labels render before the API answers.

## Angular conventions

- Components use `templateUrl` with a sibling `.html` file. No inline `template:` outside host components declared in `*.spec.ts` files.
- Async APIs in services, guards and resolvers return RxJS Observables, not Promises: no `async`/`await`/`firstValueFrom` in production code. The exceptions are `loadComponent` dynamic imports and router navigation calls (`void router.navigate(...)`); wrap other promise sources with `from(...)`.

## TypeScript coding rules

The same layout rules as the API (`@PigeonWatch/Api/CLAUDE.md`), applied to `.ts` files. Angular template control flow (`@if`, `@for`) always needs its braces and is out of scope.

- Every `if` and `return` statement is preceded by a blank line, unless it is the first statement of its enclosing block or body (function, method, constructor, accessor, arrow-function block, `if`/`else` or loop body).
- An `if`, `else`, `for` or `while` body that is a single statement on one line has no braces. A body with more than one statement, or a single statement wrapped over several lines, keeps its braces. Prettier keeps such a body on the header line when it fits (`if (!token) return null;`).

  ```ts
  const saved = readStoredCulture();

  if (!saved) return defaultCulture;

  const culture = saved.toLowerCase();

  return supportedCultures.includes(culture) ? culture : defaultCulture;
  ```

Neither rule is checked by tooling: there is no ESLint, and Prettier preserves blank lines and braces as written.
