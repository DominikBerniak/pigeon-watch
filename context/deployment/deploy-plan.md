# First Deployment Plan — PigeonWatch → Azure

## Context

`context/foundation/infrastructure.md` (bias-checked research) and `context/foundation/tech-stack.md` (stack hand-off) lock in **Azure App Service, Free (F1) tier, Linux**, plus Azure SQL (free tier), Blob Storage for photos, and Azure Static Web Apps for the Angular frontend, deployed via GitHub Actions auto-deploy-on-merge. Both projects are currently at raw CLI-scaffold state — no auth, no business logic, no CI workflow yet — so this is a genuine first deployment, not a redeploy. Scope for this pass: **API and frontend together**.

Two corrections found during research, both non-blocking for the platform choice itself:

1. **Runtime version**: both docs say ".NET 8", but `PigeonWatch/Api/PigeonWatchApi.csproj` actually targets **`net10.0`**. Verified via web research: Azure App Service Linux has native, non-container support for `DOTNETCORE|10.0` (Active LTS through Nov 2028, per [Azure's runtime support docs](https://github.com/Azure/app-service-linux-docs/blob/master/Runtime_Support/dot_net_core.md)). No container workaround needed — every `az` command below uses the moniker `DOTNETCORE:10.0`.
2. **Region, resolved through live testing, not docs alone**. The plan went through three region decisions before landing on real, working ones:
   - Originally `polandcentral` (co-location preference), ruled out because Static Web Apps doesn't support it at all, and Azure SQL's free-tier offer has a reported regional-rollout billing bug there.
   - Consolidated to a single `westeurope` region — but creating the App Service Plan there failed live with `RequestDisallowedByAzure: The selected region is currently not accepting new customers`. Per Microsoft's own troubleshooting doc, West Europe is currently the one region this new-tenant restriction applies to.
   - Tried `germanywestcentral`, `eastus2`, and `northeurope` next — all three returned `Operation cannot be completed without additional quota` (Current Limit: 0 F1 VMs) for this subscription. Free Trial/new subscriptions get a **per-region** quota of 0 for App Service compute in many regions, separate from the West Europe block.
   - **`swedencentral` actually worked** — live-tested by creating and then deleting a real F1 App Service Plan and a real free-tier SQL database there; both succeeded (`"tier": "LinuxFree"`, `"useFreeLimit": true`, no billing-bug symptoms).
   - Azure Static Web Apps' supported region list is a fixed platform constraint (confirmed via `az provider show --namespace Microsoft.Web --query "resourceTypes[?resourceType=='staticSites'].locations"`): Central US, East US 2, West US 2, West Europe, East Asia — `swedencentral` is not among them, and West Europe is still blocked for new resources. **`eastus2`** was live-tested and worked cleanly for a Static Web App (Free tier).

   **Final regions**: App Service (F1), Azure SQL (free tier), and Blob Storage all go in **`swedencentral`**; Static Web Apps goes in **`eastus2`**. Static Web Apps' actual content is served through Azure's global CDN regardless of which of its 5 supported regions you pick, so this split shouldn't meaningfully affect latency for end users. The resource group itself (`pigeon-watch-rg`) was created with `--location westeurope` before this was discovered — that's harmless, since a resource group's own location is just metadata for the group object and doesn't constrain where its resources physically live (confirmed: the plan and DB tests both landed correctly in `swedencentral` inside this group).

**Execution note**: `az` CLI is installed and authenticated on this machine (confirmed via `az account show`), so commands below are run directly rather than relayed — this file tracks what's actually been executed, not just planned. The `Microsoft.Sql` resource provider needed a one-time `az provider register --namespace Microsoft.Sql` before any SQL resource would create (standard, unrelated to the region issues above).

### Layered API, migrate job and migration runbook (change `persistence-wiring-smoke`, Phase 5)

**Deployed project changed.** The API is now split into layered projects under `PigeonWatch/Api/` (`WebApi.Host`, `WebApi`, `DependencyInjection`, `BusinessLogic`, `Data`, `BusinessObjects`, plus `ArchitectureTests`; rules in `PigeonWatch/Api/CLAUDE.md`). The deployed host is `PigeonWatch/Api/WebApi.Host/PigeonWatch.WebApi.Host.csproj` (assembly `PigeonWatch.WebApi.Host`, formerly `PigeonWatchApi`); the publish output path `PigeonWatch/Api/publish` and the `PigeonWatch/Api/**` trigger are unchanged. The App Service startup command is pinned to `dotnet PigeonWatch.WebApi.Host.dll` (`az webapp config set --name pigeonwatch-api --resource-group pigeon-watch-rg --startup-file "dotnet PigeonWatch.WebApi.Host.dll"`), and `azure/webapps-deploy` runs with `clean: true` so `wwwroot` is emptied before each deploy.

**Incident on the first layered deploy (2026-10-03, run 37146971832)**: the deploy overwrote `wwwroot` without cleaning it, so the old `PigeonWatchApi.dll`/`.runtimeconfig.json`/`.deps.json` stayed next to the new host. Oryx found two `*.runtimeconfig.json` files, could not pick a startup DLL and fell back to the default `hostingstart.dll`, so every route returned 404 and the post-deploy probe failed. The migration in the same run had already succeeded. Mitigated by hand: the four stale `PigeonWatchApi.*` files were deleted through the Kudu VFS API and the app restarted, after which `/health/db` returned 200. Fixed for good by the pinned startup command and `clean: true`. Any future rename of the host assembly hits the same trap without them. The EF Core context and migrations live in `PigeonWatch/Api/Data`, so every `dotnet ef` command takes `--project PigeonWatch/Api/Data/PigeonWatch.Data.csproj --startup-project PigeonWatch/Api/WebApi.Host/PigeonWatch.WebApi.Host.csproj`.

**Workflow.** `deploy-api.yml` now runs `test` (architecture tests) → `migrate` → `build-and-deploy`, serialized by `concurrency: deploy-api`. `migrate` builds a self-contained `linux-x64` EF migration bundle, logs in with the OIDC service principal, opens a firewall rule for the runner IP named `gh-runner-<run_id>-<run_attempt>`, runs `./efbundle --connection "$SQL_CONN"` (`Authentication=Active Directory Default`, retried 5× 30 s apart), and deletes the rule under `if: always()`. A failed test or migration blocks the deploy. After deploy, the `Probe API` step (`curl -f --retry 10 ... /configuration/client`) fails the run if the live API does not answer. Since change `register-and-login` the probe no longer touches the database (it used to call `/health/db`). `api-pr-checks.yml` builds the solution, runs the architecture and API unit tests, checks that the migrations match the model, and builds and unit-tests the frontend on every PR to `main` (required status checks `architecture-tests` and `frontend-build-and-test`).

**Live probe.** `GET https://pigeonwatch-api.azurewebsites.net/configuration/client` is anonymous, publicly cacheable (`Cache-Control: public, max-age=300`) and does not touch the database, so the probe (and any uptime monitor) never wakes `pigeonwatch-db`. The former `GET /health/db` smoke probe and its `SMOKE_CHECK` table were removed in change `register-and-login` (migration `RemoveSmokeCheck`, the one approved exception to the additive-migrations rule below: the table's only consumer was removed in the same deploy, so the old build's `/health/db` could fail only between the `migrate` and `build-and-deploy` jobs). `GET /health/db` now returns 404.

**Additive migrations rule.** `migrate` runs before `build-and-deploy`, so a migration can land while the deploy that follows it fails, leaving the previous build running against the new schema. Every migration must be additive and backward compatible with the previously deployed build (add tables/nullable columns; no drops, renames or type narrowing in the same release that stops using them).

**Manual migration-down (rollback runbook).** CI never migrates down. When a reverted deploy needs the schema rolled back:

1. Find the target: `dotnet ef migrations list --project PigeonWatch/Api/Data/PigeonWatch.Data.csproj --startup-project PigeonWatch/Api/WebApi.Host/PigeonWatch.WebApi.Host.csproj` (the migration before the one to undo).
2. Open a temporary firewall rule for your client IP: `az sql server firewall-rule create --resource-group pigeon-watch-rg --server pigeonwatch-sql --name rollback-<date> --start-ip-address <ip> --end-ip-address <ip>`.
3. Run it as yourself, the SQL Entra admin (see the Phase 3 AD-admin item). Neither the CI service principal nor the API's managed identity can be used: the CI principal `pigeon-watch-api-github-oidc` has only a GitHub federated credential and no workflow accepts a target migration, and the managed identity has no `db_ddladmin`. After `az login`, at the reverted commit run `dotnet ef database update <previous-migration> --project PigeonWatch/Api/Data/PigeonWatch.Data.csproj --startup-project PigeonWatch/Api/WebApi.Host/PigeonWatch.WebApi.Host.csproj --connection "<SQL_CONN>"`, with `SQL_CONN` as in `deploy-api.yml` (its `Authentication=Active Directory Default` picks up the `az login` session). A bundle also works (`.\efbundle.exe --connection "<SQL_CONN>" <previous-migration>`), but build it with `-r win-x64` for this machine, because the CI bundle is `linux-x64`.
4. Verify while the rule is still open: `sqlcmd -S pigeonwatch-sql.database.windows.net -d pigeonwatch-db -G -Q "SELECT MIGRATION_ID FROM EF_MIGRATIONS_HISTORY"` and `curl.exe -f https://pigeonwatch-api.azurewebsites.net/configuration/client` (or `/health/db` if the rollback target predates change `register-and-login`).
5. Delete the temporary firewall rule and confirm `az sql server firewall-rule list ... --query "[].name" -o tsv` shows only `AllowAzureServices`.

### Auth, rate limiting and Data Protection keys (change `register-and-login`, Phase 2)

The API now issues ASP.NET Core Identity bearer and refresh tokens and limits `auth/login` and `account/register` to 10 requests per minute per client IP (`auth/refresh` is exempt).

- [ ] App setting `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`, set by hand before the S-01 API merge: `az webapp config appsettings set --name pigeonwatch-api --resource-group pigeon-watch-rg --settings ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`. Linux App Service sits behind a reverse proxy, so without it `HttpContext.Connection.RemoteIpAddress` is the front end's address and every client shares one rate-limit partition. Verify with `az webapp config appsettings list --name pigeonwatch-api --resource-group pigeon-watch-rg --query "[?name=='ASPNETCORE_FORWARDEDHEADERS_ENABLED']"`, then check that 11 quick logins from one network return `429` while a phone on mobile data can still log in in the same minute.
- **No signing key.** Identity bearer tokens are not JWTs; they are protected by the Data Protection key ring, so there is no JWT secret to set or rotate.
- **Data Protection keys** are persisted automatically to `/home/ASP.NET/DataProtection-Keys` (App Service sets `HOME` and `WEBSITE_INSTANCE_ID`). `/home` is persistent storage outside the `clean: true` wwwroot, so deploys and restarts keep the keys and issued tokens stay valid. Deleting that folder, or moving to deployment slots (which do not share `/home` keys), invalidates every access and refresh token and logs every user out. Verify once after the first S-01 deploy: log in, run `az webapp restart --name pigeonwatch-api --resource-group pigeon-watch-rg`, then `Invoke-RestMethod -Method Post -Uri https://pigeonwatch-api.azurewebsites.net/auth/refresh -ContentType 'application/json' -Body '{"refreshToken":"<token issued before the restart>"}'` must return a new token pair (a `401` means the keys were lost).
- **Production CORS** stays on the App Service platform (`az webapp cors add`, Phase 5). The in-app policy covers only `http://localhost:4200`. Live preflight check: `curl.exe -i -X OPTIONS https://pigeonwatch-api.azurewebsites.net/configuration/general -H "Origin: https://wonderful-sea-07000d90f.6.azurestaticapps.net" -H "Access-Control-Request-Method: GET" -H "Access-Control-Request-Headers: authorization"`.

## Accepted risks not yet empirically verified

- **First `/health/db` call after Azure SQL auto-pause can return 503** (observed 2026-10-03, change `persistence-wiring-smoke` Phase 5 check 5.6): with `pigeonwatch-db` in `Paused` state the first probe returned 503 and an immediate second call returned 200. `EnableRetryOnFailure` (default 6 retries) plus the 30 s connect timeout did not cover the resume, or the F1 front end timed out while app and database woke together; the cause was not visible because `DatabaseHealthService` swallowed the exception without logging it (it now logs it at Warning, implementation review F2, 2026-10-04). Follow-up: read that log after the next post-pause 503 and tune the retry budget / `Connect Timeout` before a user-facing slice depends on the first request after idle. **Update (change `register-and-login`):** `/health/db` and `DatabaseHealthService` are gone. A paused or unreachable database now surfaces from any endpoint as `503` ProblemDetails (`title: "Service warming up"`) with `Retry-After: 10` from `DatabaseUnavailableExceptionHandler`, never `500`, and the SPA's warm-up panel retries for up to ~2 minutes. Tuning EF's retry budget and `Connect Timeout` is still an open follow-up.
- **Anonymous `/health/db` can exhaust the free-tier vCore allowance** (found in the `persistence-wiring-smoke` implementation review, 2026-10-04). Every call wakes `pigeonwatch-db`, which runs on the free limit with `--free-limit-exhaustion-behavior AutoPause`. At the 0.5 vCore minimum, the 100k vCore-second monthly allowance is about 55 h online. Each wake keeps the database online for at least the auto-pause delay, so roughly hourly calls from anyone (including an uptime monitor) could use up the month within days and leave the database paused until the month ends. Accepted for the throwaway probe. **Exit:** remove or secure `/health/db` no later than S-01, and do not point an uptime monitor at it. **Closed (change `register-and-login`, S-01):** `/health/db` and the `SMOKE_CHECK` table are removed, and the deploy probe calls `GET /configuration/client`, which does not touch the database. An uptime monitor, if added, must also use `/configuration/client` or `/resources/en`, never an endpoint that reads the database.
- **F1 cold-start after genuine 20+ min idle**: theoretical/documented only (Azure's own F1-tier docs describe idle-sleep behavior). The ~32s figure captured above is a proxy (cold container start, not idle-sleep wake), and is the best current evidence — treat actual idle cold-start latency as potentially higher until directly observed.
